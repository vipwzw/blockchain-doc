### 2.1 JAM：成为验证者

#### 2.1.1 基本要求

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    JAM 验证者要求                                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │

│                                                                         │
│   密钥要求（336 字节密钥组合）：                                          │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │  k_b: Bandersnatch 密钥   │  32 字节  │  Ring VRF 票据       │   │
│   │  k_e: Ed25519 密钥        │  32 字节  │  签名验证            │   │
│   │  k_l: BLS 密钥            │  144 字节 │  GRANDPA 聚合签名    │   │
│   │  k_m: 元数据              │  128 字节 │  网络地址等          │   │
│   └────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│   质押要求：由链上质押服务定义（非核心协议）                              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 2.1.2 注册流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    JAM 验证者注册流程                                    │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  步骤 1: 生成密钥                                                        │
│  ────────────────                                                       │
│  • 生成 Bandersnatch 密钥对（用于 Ring VRF）                            │
│  • 生成 Ed25519 密钥对（用于普通签名）                                   │

│                                                                         │
│  步骤 2: 质押代币                                                        │
│  ────────────────                                                       │
│  • 通过链上质押服务提交质押                                              │
│  • 质押金额由质押服务规则决定                                            │
│  • 质押足够才能进入候选验证者集                                          │
│                                                                         │
│  步骤 3: 提交密钥到 ι (候选集)                                           │

│                                                                         │
│  步骤 4: 等待纪元轮换                                                    │
│  ────────────────────                                                   │
│  • 纪元 N: 加入 ι (候选集)                                              │
│  • 纪元 N+1: 进入 γ_P (待定集)                                          │
│  • 纪元 N+2: 成为 κ (活跃集)，开始参与共识                               │

│                                                                         │
│  步骤 5: 运行节点                                                        │
│  ──────────────                                                         │
│  • 部署 JAM 节点软件                                                     │
│  • 导入私钥                                                              │
│  • 保持在线，参与出块和验证                                              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 2.2.3 存款合约交互

```solidity
// 以太坊存款合约接口（简化）
interface IDepositContract {
    // 存款事件
    event DepositEvent(
        bytes pubkey,           // BLS 公钥 (48 字节)
        bytes withdrawal_credentials,  // 提款凭证 (32 字节)
        bytes amount,           // 存款金额 (8 字节, Little Endian)
        bytes signature,        // BLS 签名 (96 字节)
        bytes index             // 存款索引
    );
    
    // 存款函数
    function deposit(
        bytes calldata pubkey,
        bytes calldata withdrawal_credentials,
        bytes calldata signature,
        bytes32 deposit_data_root
    ) external payable;
}

// 存款数据结构
struct DepositData {
    bytes48 pubkey;                    // 验证者 BLS 公钥
    bytes32 withdrawal_credentials;    // 提款凭证
    uint64 amount;                     // 存款金额 (Gwei)
    bytes96 signature;                 // 对存款消息的 BLS 签名
    bytes32 deposit_data_root;         // 存款数据的哈希根
}
```

## 3. 出块机制

### 3.1 JAM：SAFROLE 出块协议

#### 3.1.1 核心概念

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    JAM SAFROLE 出块机制                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   核心创新：Ring VRF 票据系统                                            │
│                                                                         │
│   目标：                                                                 │
│   ✓ 每个时间槽只有一个验证者有出块权                                     │
│   ✓ 出块者身份在出块前保持匿名                                           │
│   ✓ 所有验证者出块机会平等                                               │
│   ✓ 生成高质量链上随机数                                                 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 3.1.2 票据竞争机制

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Ring VRF 票据竞争流程                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  阶段 1: 票据提交期（纪元前半段，槽位 0-299）                            │
│  ─────────────────────────────────────────                              │
│                                                                         │
│  验证者 A ──┐                                                           │
│  验证者 B ──┼──▶ Ring VRF 签名 ──▶ 提交票据到链上                       │
│  验证者 C ──┘                                                           │
│  ...                                                                    │
│                                                                         │
│  每个验证者：                                                            │
│  • 使用 Bandersnatch 私钥生成 Ring VRF 签名                             │
│  • 签名消息 = 纪元随机数 η₂ ⌢ 尝试索引                                   │
│  • 票据分数 y = VRF 输出的前 32 字节                                     │
│  • 每个验证者最多提交 N = 2 个票据                                       │
│                                                                         │
│  阶段 2: 票据收集                                                        │
│  ─────────────────                                                      │
│                                                                         │
│  γ_A (票据累加器) 保留分数最低的 600 个票据                              │
│                                                                         │
│  排序：票据按分数从低到高排序                                            │
│  [票据₀, 票据₁, 票据₂, ... 票据₅₉₉]                                      │
│   ↑最低分                           ↑最高分                              │
│                                                                         │
│  阶段 3: 密封密钥序列生成                                                │
│  ───────────────────────                                                │
│                                                                         │
│  使用 Outside-In 排列函数 Z：                                            │
│  原序列: [0, 1, 2, 3, ..., 598, 599]                                    │
│  排列后: [0, 599, 1, 598, 2, 597, ...]                                  │
│                                                                         │
│  目的：将最优秀的票据分散到纪元的开始和结束                               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 3.1.3 出块流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    JAM 出块详细流程                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  时间槽 T 到来时：                                                       │
│                                                                         │
│  1. 确定出块者                                                           │
│     ────────────                                                        │
│     • 查询 γ_S[T mod E] 获取该槽位的密封密钥                             │
│     • 如果是票据模式：密封密钥 = 票据的 VRF 输出                         │
│     • 如果是回退模式：密封密钥 = 验证者的 Bandersnatch 公钥              │
│                                                                         │
│  2. 构建区块                                                             │
│     ────────                                                            │
│     • 收集交易和外部数据                                                 │
│     • 构建区块头 H                                                       │
│     • 计算状态转换                                                       │
│                                                                         │
│  3. 区块签名                                                             │
│     ────────                                                            │
│     • 密封签名 H_S: 使用 Bandersnatch 签名区块头（不含 H_S）             │
│     • VRF 输出 H_V: 签名熵累加消息，提供链上随机数                       │
│                                                                         │
│  4. 广播区块                                                             │
│     ────────                                                            │
│     • 将完整区块广播给其他验证者                                         │
│                                                                         │
│  5. 验证接收                                                             │
│     ────────                                                            │
│     • 其他节点验证签名有效性                                             │
│     • 验证出块者确实拥有该槽位的出块权                                   │
│     • 验证状态转换正确性                                                 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 3.1.4 回退模式

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    SAFROLE 回退模式                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  触发条件：                                                              │
│  • 纪元结束时，票据累加器 γ_A 未饱和（少于 600 个票据）                  │
│  • 或者在纪元切换时发生跨纪元跳跃                                        │
│                                                                         │
│  回退机制：                                                              │
│  • 使用确定性伪随机函数 F(η₂, κ) 生成密封密钥序列                        │
│  • 从验证者集 κ 中按伪随机顺序选择 600 个密钥                            │
│  • 每个槽位直接使用验证者的 Bandersnatch 公钥                            │
│                                                                         │
│  安全降级：                                                              │
│  • 回退模式下，出块者身份不再匿名                                        │
│  • 可能受到 MEV 攻击或 DoS 攻击                                          │
│  • 系统会尽快恢复到正常票据模式                                          │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.2 以太坊 PoS：出块机制

#### 3.2.1 核心概念

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    以太坊 PoS 出块机制                                   │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   核心组件：RANDAO + 提议者选择算法                                      │
│                                                                         │
│   目标：                                                                 │
│   ✓ 按质押比例分配出块机会                                               │
│   ✓ 伪随机选择提议者                                                     │
│   ✓ 支持大规模验证者参与                                                 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 3.2.2 提议者选择算法

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    以太坊提议者选择流程                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  1. RANDAO 随机数生成                                                    │
│     ──────────────────                                                  │
│     • 每个区块提议者贡献一个 RANDAO reveal                               │
│     • reveal = BLS_Sign(私钥, epoch)                                    │
│     • 新 RANDAO = Hash(旧 RANDAO ⊕ reveal)                              │
│                                                                         │
│  2. 提议者选择                                                           │
│     ────────────                                                        │
│     for each slot in epoch:                                             │
│         seed = Hash(RANDAO || slot || domain)                           │
│         # 按有效余额加权随机选择                                         │
│         proposer = weighted_random_select(                              │
│             validators,                                                 │
│             weights = effective_balances,                               │
│             seed = seed                                                 │
│         )                                                               │
│                                                                         │
│  3. 委员会分配                                                           │
│     ────────────                                                        │
│     • 每个 epoch 的 32 个 slot，每个 slot 有多个委员会                   │
│     • 验证者被伪随机分配到委员会                                         │
│     • 每个验证者每个 epoch 恰好证明一次                                  │
│                                                                         │
│  关键点：                                                                │
│  ⚠️ 提议者列表在 epoch 开始时可以被计算出来                              │
│  ⚠️ 这意味着未来出块者的身份是公开的                                     │
│  ⚠️ 可能受到针对性攻击（与 JAM 的匿名性形成对比）                        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 3.2.3 出块详细流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    以太坊 PoS 出块详细流程                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Slot N 开始 (第 0 秒):                                                  │
│                                                                         │
│  1. 提议者构建区块                                                       │
│     ────────────────                                                    │
│     • 执行层：从内存池选择交易，执行 EVM                                 │
│     • 共识层：包含证明、同步委员会签名等                                 │
│     • 可选：与 MEV-Boost 交互获取 builder 区块                           │
│                                                                         │
│  2. 区块签名和广播 (第 0-4 秒)                                           │
│     ──────────────────────────                                          │
│     • 使用 BLS 私钥签名区块                                              │
│     • 广播到 P2P 网络                                                    │
│                                                                         │
│  3. 证明阶段 (第 4-8 秒)                                                 │
│     ─────────────────────                                               │
│     • 委员会验证者创建证明 (attestation)                                 │
│     • 证明包含：                                                         │
│       - 头部投票 (head vote): 对链头的投票                               │
│       - 源检查点 (source): 上一个 justified 检查点                       │
│       - 目标检查点 (target): 当前 epoch 的检查点                         │
│     • 使用 BLS 签名证明                                                  │
│     • 广播证明                                                           │
│                                                                         │
│  4. 聚合阶段 (第 8-12 秒)                                                │
│     ─────────────────────                                               │
│     • 选中的聚合者收集同委员会的证明                                     │
│     • BLS 签名聚合                                                       │
│     • 广播聚合证明                                                       │
│                                                                         │
│  Slot N+1 开始:                                                          │
│     • 下一个提议者将聚合证明打包到新区块                                 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 4. 最终性共识

### 4.1 JAM：GRANDPA 最终性

#### 4.1.1 核心原理

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    JAM GRANDPA 最终性协议                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   类型：拜占庭容错 (BFT) 最终性协议                                       │
│   特点：独立于区块生产，可以一次最终化多个区块                           │
│                                                                         │
│   安全阈值：                                                             │
│   • 需要 > 2/3 验证者投票才能最终化                                      │
│   • 可容忍 < 1/3 拜占庭节点                                              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 4.1.2 GRANDPA 投票流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    GRANDPA 两轮投票流程                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  第一轮：Pre-Vote（预投票）                                              │
│  ─────────────────────────                                              │
│                                                                         │
│  所有验证者广播 pre-vote：                                               │
│  • 选择自己认为的最佳区块                                                │
│  • 签名：BLS_Sign(验证者私钥, (轮次, 区块哈希))                          │
│                                                                         │
│  收集 pre-votes：                                                        │
│  • 等待收到 > 2/3 验证者的 pre-votes                                     │
│  • 计算 "ghost" - 获得最多 pre-votes 的链                                │
│                                                                         │
│  第二轮：Pre-Commit（预提交）                                            │
│  ───────────────────────────                                            │
│                                                                         │
│  所有验证者广播 pre-commit：                                             │
│  • 为 ghost 链上能被最终化的最高区块投票                                 │
│  • 签名：BLS_Sign(验证者私钥, (轮次, 区块哈希))                          │
│                                                                         │
│  最终化判定：                                                            │
│  • 当区块收到 > 2/3 的 pre-commits 时                                    │
│  • 该区块及其所有祖先被最终化                                            │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  区块 A ◄── 区块 B ◄── 区块 C ◄── 区块 D ◄── 区块 E            │   │
│  │     │                             ▲                             │   │
│  │     └─────── 已最终化 ────────────┘                             │   │
│  │                               pre-commits > 2/3                 │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 4.1.3 GRANDPA 签名聚合

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    GRANDPA BLS 签名聚合                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  单个验证者签名：                                                        │
│  σᵢ = BLS_Sign(skᵢ, message)                                           │
│                                                                         │
│  聚合签名（所有 pre-commits）：                                          │
│  σ_agg = σ₁ + σ₂ + σ₃ + ... + σₙ                                        │
│                                                                         │
│  验证聚合签名：                                                          │
│  BLS_Verify(pk₁ + pk₂ + ... + pkₙ, message, σ_agg) = true               │
│                                                                         │
│  优势：                                                                  │
│  • 无论多少签名，聚合后大小固定 (96 字节)                                │
│  • 验证效率高                                                            │
│  • 减少网络带宽和存储                                                    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 4.2 以太坊 PoS：Casper FFG 最终性

#### 4.2.1 核心原理

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    以太坊 Casper FFG 最终性协议                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   类型：检查点最终性 (Checkpoint Finality)                               │
│   特点：每个 epoch 产生一个检查点，两个 epoch 后最终化                   │
│                                                                         │
│   关键概念：                                                             │
│   • Checkpoint（检查点）：每个 epoch 第一个 slot 的区块                  │
│   • Justified（合理化）：获得 2/3+ 验证者投票                            │
│   • Finalized（最终化）：连续两个 justified 检查点                       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 4.2.2 检查点投票流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Casper FFG 检查点投票                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Epoch N:                                                                │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  Slot 0  │ Slot 1 │ ... │ Slot 31                                │   │
│  │    ↓                                                             │   │
│  │ Checkpoint N                                                     │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  每个验证者在其分配的 slot 创建证明 (Attestation)：                      │
│  {                                                                      │
│      source: Checkpoint(N-1),      // 源检查点                          │
│      target: Checkpoint(N),        // 目标检查点                        │
│      head: 当前链头区块哈希,                                            │
│      signature: BLS 签名                                                │
│  }                                                                      │
│                                                                         │
│  Justification 规则：                                                    │
│  • 如果 Checkpoint(N) 收到 2/3+ 总质押的投票                             │
│  • 且投票的 source 是 Checkpoint(N-1)                                   │
│  • 则 Checkpoint(N) 被 Justified                                        │
│                                                                         │
│  Finalization 规则：                                                     │
│  • 如果 Checkpoint(N) 是 Justified                                      │
│  • 且 Checkpoint(N-1) 也是 Justified                                    │
│  • 则 Checkpoint(N-1) 被 Finalized                                      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 4.2.3 最终性时间线

```
时间线（理想情况）：
────────────────────────────────────────────────────────────────────────

Epoch N-1        Epoch N          Epoch N+1        Epoch N+2
   │               │                 │                │
   ▼               ▼                 ▼                ▼
┌──────┐       ┌──────┐          ┌──────┐         ┌──────┐
│ CP   │ ───▶  │ CP   │  ───▶    │ CP   │  ───▶   │ CP   │
│ N-1  │       │ N    │          │ N+1  │         │ N+2  │
└──────┘       └──────┘          └──────┘         └──────┘
   │               │                 │
   │               │                 └──▶ CP(N) Finalized!
   │               └──▶ CP(N) Justified
   └──▶ CP(N-1) Finalized

最终性延迟：约 2 个 epoch ≈ 12.8 分钟
```

### 4.3 最终性对比

| 特性 | JAM (GRANDPA) | 以太坊 PoS (Casper FFG) |
|------|---------------|------------------------|
| **类型** | BFT 投票 | 检查点投票 |
| **最终性延迟** | ~2-3 个区块 (~12-18秒) | 2 个 epoch (~12.8分钟) |
| **投票频率** | 每轮一次 | 每个 epoch 一次 |
| **可最终化区块数** | 一次可最终化多个 | 每次最终化一个 epoch |
| **安全阈值** | 2/3+ 验证者 | 2/3+ 总质押 |
| **签名方式** | BLS 聚合 | BLS 聚合 |

#### 5.1.1 多密钥体系

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    JAM 多密钥签名体系                                    │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  1. Bandersnatch 密钥 (k_b) - 32 字节                                   │
│     ───────────────────────────────────                                 │
│     算法：Bandersnatch 椭圆曲线 (嵌入 BLS12-381)                         │
│     用途：                                                               │
│     • Ring VRF 票据生成（匿名证明属于验证者集合）                        │
│     • 区块密封签名 (H_S)                                                │
│     • VRF 随机数输出 (H_V)                                              │
│                                                                         │
│     Ring VRF 签名：                                                      │
│     ┌─────────────────────────────────────────────────────────────┐    │
│     │  输入：                                                      │    │
│     │  • 私钥 sk                                                   │    │
│     │  • 消息 m                                                    │    │
│     │  • Ring (所有验证者公钥集合)                                 │    │
│     │                                                              │    │
│     │  输出：                                                      │    │
│     │  • 签名 σ (证明签名者在 Ring 中)                             │    │
│     │  • VRF 输出 y (确定性随机数)                                 │    │
│     │                                                              │    │
│     │  特性：无法确定是 Ring 中哪个成员签名                        │    │
│     └─────────────────────────────────────────────────────────────┘    │
│                                                                         │
│  2. Ed25519 密钥 (k_e) - 32 字节                                        │
│     ────────────────────────────────                                    │
│     算法：Ed25519 (Curve25519 上的 EdDSA)                               │
│     用途：                                                               │
│     • 普通消息签名                                                      │
│     • 验证者身份验证                                                    │
│     • 网络层消息认证                                                    │
│                                                                         │
│     签名格式：                                                          │
│     σ = Ed25519_Sign(sk, message)  // 64 字节签名                       │
│                                                                         │
│  3. BLS 密钥 (k_l) - 144 字节                                           │
│     ──────────────────────────────                                      │
│     算法：BLS12-381 曲线上的 BLS 签名                                   │
│     用途：                                                               │
│     • GRANDPA 最终性投票                                                │
│     • 签名聚合（多个签名合并为一个）                                    │
│                                                                         │
│     聚合流程：                                                          │
│     ┌─────────────────────────────────────────────────────────────┐    │
│     │  单个签名：σᵢ = BLS_Sign(skᵢ, message)                      │    │
│     │  聚合签名：σ_agg = σ₁ + σ₂ + ... + σₙ                        │    │
│     │  公钥聚合：pk_agg = pk₁ + pk₂ + ... + pkₙ                    │    │
│     │  验证：BLS_Verify(pk_agg, message, σ_agg)                    │    │
│     └─────────────────────────────────────────────────────────────┘    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 5.2.1 BLS12-381 签名

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    以太坊 PoS BLS12-381 签名体系                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  密钥结构：                                                              │
│  ─────────                                                              │
│  • 私钥：32 字节标量                                                    │
│  • 公钥：48 字节 G1 点                                                  │
│  • 签名：96 字节 G2 点                                                  │
│                                                                         │
│  签名算法：BLS (Boneh-Lynn-Shacham)                                     │
│  曲线：BLS12-381                                                        │
│                                                                         │
│  签名流程：                                                              │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  1. 消息哈希：H(message) → G2 点                                 │   │
│  │  2. 签名：σ = sk × H(message)                                    │   │
│  │  3. 验证：e(pk, H(m)) == e(G1, σ)                                │   │
│  │     其中 e 是双线性配对函数                                       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  聚合特性：                                                              │
│  ─────────                                                              │
│  • 相同消息的签名可以聚合                                               │
│  • σ_agg = σ₁ + σ₂ + ... + σₙ                                          │
│  • 验证：e(pk₁ + pk₂ + ... + pkₙ, H(m)) == e(G1, σ_agg)                │
│                                                                         │
│  不同消息的聚合（更复杂）：                                              │
│  • 需要单独验证每个消息                                                 │
│  • e(pk₁, H(m₁)) × e(pk₂, H(m₂)) × ... == e(G1, σ_agg)                 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 7. 经济激励与惩罚

### 7.1 JAM 经济机制

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    JAM 经济机制                                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │

│  ───────────────────────                                                │

│  • 验证奖励：参与 GRANDPA 投票获得奖励                                  │
│  • 工作报告奖励：担保和验证工作报告                                     │
│                                                                         │
│  惩罚：                                                                  │
│  ─────                                                                  │
│  • 离线惩罚：长时间不参与可能被踢出                                     │
│  • Slashing：                                                           │
│    - 双重签名（同一槽位签两个区块）                                     │
│    - 无效工作报告担保                                                   │
│    - 违规者加入 ψ_O，纪元切换时被踢出                                   │
│                                                                         │
│  特点：所有验证者奖励机会平等                                           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 7.2 以太坊 PoS 经济机制

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    以太坊 PoS 经济机制                                   │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  奖励：                                                                  │
│  ─────                                                                  │
│  • 证明奖励（主要来源）：                                               │
│    - 正确的源检查点投票                                                 │
│    - 正确的目标检查点投票                                               │
│    - 正确的链头投票                                                     │
│    - 及时包含奖励                                                       │
│                                                                         │
│  • 提议者奖励：                                                          │
│    - 包含证明的奖励                                                     │
│    - 同步委员会签名奖励                                                 │
│    - Slashing 举报奖励                                                  │
│                                                                         │
│  • 同步委员会奖励：额外的签名奖励                                       │
│                                                                         │
│  惩罚：                                                                  │
│  ─────                                                                  │
│  • 离线惩罚：                                                            │
│    - 错过证明：损失应得奖励                                             │
│    - 不活跃泄漏：长时间离线时逐步扣除余额                               │
│                                                                         │
│  • Slashing（严重违规）：                                               │
│    - 提议者 Slashing：签署两个不同区块                                  │
│    - 证明者 Slashing：环绕投票或双重投票                                │
│    - 初始惩罚：1/32 有效余额                                            │
│    - 关联惩罚：与同时被 slash 的验证者数量成比例                        │
│    - 强制退出 + 36天锁定期                                              │
│                                                                         │
│  年化收益率（APR）：                                                    │
│  ─────────────────                                                     │
│  • 取决于总质押量                                                       │
│  • 约 3-5% APR（当前）                                                  │
│  • 公式：base_reward = effective_balance × base_reward_factor           │
│          / sqrt(total_active_balance)                                   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 8. 总结对比表

### 8.1 核心特性对比

| 特性 | JAM | 以太坊 PoS |
|------|-----|-----------|
| **共识类型** | SAFROLE + GRANDPA | LMD-GHOST + Casper FFG |
| **验证者数量** | 固定 1023 | 无上限 (~100万+) |
| **最低质押** | 由服务定义 | 32 ETH |
| **权重分配** | 平等 | 按质押比例 |
| **出块时间** | 6 秒 | 12 秒 |
| **最终性时间** | ~12-18 秒 | ~12.8 分钟 |
| **出块者匿名** | ✅ Ring VRF | ❌ 提前可知 |

### 8.2 密码学对比

| 特性 | JAM | 以太坊 PoS |
|------|-----|-----------|
| **主要签名算法** | Bandersnatch + Ed25519 + BLS | BLS12-381 |
| **VRF 支持** | ✅ Ring VRF | ❌ 使用 RANDAO |
| **签名聚合** | ✅ BLS | ✅ BLS |
| **匿名证明** | ✅ Ring 签名 | ❌ 无 |
| **随机数生成** | VRF 输出 | RANDAO 累积 |

### 8.3 安全特性对比

| 特性 | JAM | 以太坊 PoS |
|------|-----|-----------|
| **拜占庭容错** | 1/3 验证者 | 1/3 总质押 |
| **MEV 抵抗** | ✅ 匿名出块 | 部分 (MEV-Boost) |
| **长程攻击** | GRANDPA 防护 | 弱主观性检查点 |
| **无利害关系** | 质押惩罚 | Slashing |

### 8.4 适用场景

```
┌─────────────────────────────────────────────────────────────────────────┐
```
