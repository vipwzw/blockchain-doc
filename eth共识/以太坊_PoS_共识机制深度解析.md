# 以太坊 PoS 共识机制深度解析

> 从 PoW 到 PoS 的演进，The Merge 架构详解，多角色视角的共识流程

## 摘要

以太坊于 2022 年 9 月完成了历史性的 "The Merge" 升级，从工作量证明（PoW）转向权益证明（PoS）共识机制。此后经历了 Shanghai/Capella（启用提款）、Dencun（Proto-Danksharding）、Pectra（验证者合并/MaxEB）等重要升级。本文深入解析以太坊 PoS 的设计原理，包括 LMD-GHOST 分叉选择规则与 Casper FFG 最终性机制的协同工作，并从验证者、质押者、客户端软件、网络层等多个角色视角详细介绍共识的完整流程。

> **术语说明**：The Merge 前，PoS 共识组件称为 "Beacon Chain"。合并后，官方更倾向使用"共识层"（Consensus Layer）一词，与"执行层"（Execution Layer）对应。本文采用现代术语。

**关键词**：以太坊、权益证明、Casper FFG、LMD-GHOST、共识层、验证者

#### 1.1.2 权益证明（PoS）核心理念

PoS 用经济博弈替代算力竞争：

$$\text{出块权重} \propto \text{质押金额}$$

#### 1.3.2 经济安全性

以太坊 PoS 的安全性由质押的 ETH 价值支撑：

$$\text{攻击成本} \geq \frac{1}{3} \times \text{总质押量} \times \text{ETH价格}$$

**当前数据（2025年）**：
- 总质押量：~34,000,000+ ETH
- 攻击成本：> 总质押量的 1/3 × ETH 价格
- 经济安全性随 ETH 价格波动

#### 1.3.3 Slashing 惩罚机制

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      Slashing 触发条件                                   │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   1. 双重提议（Double Proposal）                                        │
│      ─────────────────────────                                         │
│      同一 slot 提议两个不同区块                                         │
│                                                                         │
│      Slot N: 验证者 V 提议 Block A                                      │
│      Slot N: 验证者 V 提议 Block B  ← 违规！                            │
│                                                                         │
│   2. 环绕投票（Surround Vote）                                          │
│      ─────────────────────                                             │
│      新投票的 source-target 范围包围旧投票                              │
│                                                                         │
│      旧投票：source=5, target=10                                        │
│      新投票：source=4, target=11  ← 违规！(4<5 且 11>10)                │
│                                                                         │
│   3. 双重投票（Double Vote）                                            │
│      ─────────────────────                                             │
│      同一 epoch 为不同区块投票                                          │
│                                                                         │
│      Epoch N: 投票 target=Block A                                       │
│      Epoch N: 投票 target=Block B  ← 违规！                             │
│                                                                         │
│   惩罚规模：                                                            │
│   • 初始惩罚：1/32 有效余额（约 1 ETH）                                 │
│   • 相关性惩罚：与同时被 slash 的验证者数量成比例                       │
│   • 最大惩罚：全部质押（如果 >1/3 验证者同时被 slash）                  │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 2.2.1 LMD-GHOST 算法

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      LMD-GHOST 分叉选择示例                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   假设有以下分叉，数字表示支持该分支的验证者权重：                      │
│                                                                         │
│                     ┌─── C (权重: 30)                                   │
│           ┌─── B ───┤                                                   │
│           │(权重:40)└─── D (权重: 10)                                   │
│   Genesis─┤                                                             │
│           │         ┌─── F (权重: 25)                                   │
│           └─── E ───┤                                                   │
│             (权重:35)└─── G (权重: 10)                                   │
│                                                                         │
│   LMD-GHOST 选择过程：                                                  │
│   ──────────────────                                                    │
│   第1步: Genesis 的子节点 B(40) vs E(35) → 选择 B                       │
│   第2步: B 的子节点 C(30) vs D(10) → 选择 C                             │
│   第3步: C 无子节点 → C 为链头                                          │
│                                                                         │
│   结果：规范链 = Genesis → B → C                                        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**算法伪代码**：

```python
def get_head(store):
    """LMD-GHOST 分叉选择规则"""
    # 从最新的 justified 检查点开始
    head = store.justified_checkpoint.root
    
    while True:
        # 获取所有子区块
        children = get_children(store, head)
        if len(children) == 0:
            return head
        
        # 选择权重最大的子区块
        head = max(children, key=lambda c: get_weight(store, c))

def get_weight(store, block):
    """计算区块的累积权重"""
    weight = 0
    for validator in store.active_validators:
        # 获取验证者的最新投票
        latest_message = store.latest_messages[validator]
        # 如果投票支持 block 或其后代
        if is_descendant(latest_message.root, block):
            weight += validator.effective_balance
    return weight
```

def get_randao_reveal(state, validator_private_key):
    """生成 RANDAO reveal"""
    epoch = get_current_epoch(state)
    domain = get_domain(state, DOMAIN_RANDAO, epoch)
    signing_root = compute_signing_root(epoch, domain)
    return bls.Sign(validator_private_key, signing_root)

def process_randao(state, body):
    """处理 RANDAO，更新随机数"""
    epoch = get_current_epoch(state)
    proposer = state.validators[get_beacon_proposer_index(state)]
    
    # 验证 RANDAO reveal
    signing_root = compute_signing_root(epoch, get_domain(state, DOMAIN_RANDAO))
    assert bls.Verify(proposer.pubkey, signing_root, body.randao_reveal)
    
    # 混合到 RANDAO 累积值
    state.randao_mixes[epoch % EPOCHS_PER_HISTORICAL_VECTOR] = xor(
        get_randao_mix(state, epoch),
        hash(body.randao_reveal)
    )

│   │                    ↓ BLS 聚合                                    │  │
│   │                                                                  │  │
│   │   聚合证明:    bits=[1,1,1,0,0,...]  sig=σ₁+σ₂+σ₃               │  │
│   │                                                                  │  │

│                                                                         │

│   • 多个 96 字节签名 → 合并为 1 个 96 字节                              │

### 4.1 LMD-GHOST 算法详解

#### 4.1.1 算法定义

**Latest Message Driven Greediest Heaviest Observed SubTree (LMD-GHOST)**

形式化定义：

设 $B$ 为所有已知区块的集合，$V$ 为活跃验证者集合，$M: V \to B$ 为每个验证者最新投票的映射。

**权重函数**：

$$W(b) = \sum_{v \in V} \mathbb{1}[M(v) \in \text{descendants}(b)] \times \text{balance}(v)$$

其中 $\text{descendants}(b)$ 包括 $b$ 自身及其所有后代区块。

**分叉选择规则**：

```python
def get_head(store, justified_checkpoint):
    """
    从 justified checkpoint 开始，递归选择权重最大的子区块
    """
    block = store.blocks[justified_checkpoint.root]
    
    while True:
        children = get_children(store, block.root)
        if len(children) == 0:
            return block.root
        
        # 选择权重最大的子区块
        block = max(
            children,
            key=lambda child: (get_weight(store, child), child.root)
        )
```

#### 4.1.3 实际实现优化：Proto-Array

**Pruning（剪枝）机制**：

```python
def on_finalized_checkpoint_updated(store, new_finalized):
    """当 finalized checkpoint 推进时，剪枝旧节点"""
    old_finalized_index = store.proto_array.indices[store.finalized_checkpoint.root]
    new_finalized_index = store.proto_array.indices[new_finalized.root]
    
    # 计算需要移除的节点数量
    nodes_to_remove = new_finalized_index - old_finalized_index
    
    # 移除 finalized 之前的所有节点
    store.proto_array.nodes = store.proto_array.nodes[nodes_to_remove:]
    
    # 更新所有索引（减去偏移量）
    for node in store.proto_array.nodes:
        if node.parent is not None:
            node.parent -= nodes_to_remove
        if node.best_child is not None:
            node.best_child -= nodes_to_remove
        if node.best_descendant is not None:
            node.best_descendant -= nodes_to_remove
    
    # 重建索引映射
    store.proto_array.indices = {
        node.root: i for i, node in enumerate(store.proto_array.nodes)
    }
    
    store.finalized_checkpoint = new_finalized
```

**权重更新流程（增量式）**：

```python
def on_attestation(store, attestation):
    """处理新证明，增量更新权重"""
    validator_index = attestation.validator_index
    new_target = attestation.data.beacon_block_root
    
    # 获取该验证者之前的投票目标
    old_target = store.latest_messages.get(validator_index)
    
    if old_target == new_target:
        return  # 投票未变化，无需更新
    
    balance = store.validators[validator_index].effective_balance
    
    # 从旧目标向上减少权重
    if old_target is not None:
        propagate_weight_change(store, old_target, -balance)
    
    # 向新目标向上增加权重
    propagate_weight_change(store, new_target, +balance)
    
    # 更新最新消息记录
    store.latest_messages[validator_index] = new_target

def propagate_weight_change(store, block_root, delta):
    """向上传播权重变化，同时更新 best_child"""
    node_index = store.proto_array.indices[block_root]
    
    while node_index is not None:
        node = store.proto_array.nodes[node_index]
        node.weight += delta
        
        # 重新评估父节点的 best_child
        if node.parent is not None:
            update_best_child_and_descendant(store, node.parent)
        
        node_index = node.parent
```

#### 4.2.2 Justification 与 Finalization

```python
def process_justification_and_finalization(state):
    """处理 epoch 边界的 justification 和 finalization"""
    
    previous_epoch = get_previous_epoch(state)
    current_epoch = get_current_epoch(state)
    
    # 获取投票权重
    previous_epoch_target_balance = get_attesting_balance(
        state, 
        get_matching_target_attestations(state, previous_epoch)
    )
    current_epoch_target_balance = get_attesting_balance(
        state,
        get_matching_target_attestations(state, current_epoch)
    )
    
    total_active_balance = get_total_active_balance(state)
    
    # Justification 规则
    # 如果 2/3+ 质押投票给某检查点，该检查点被 justified
    if previous_epoch_target_balance * 3 >= total_active_balance * 2:
        state.previous_justified_checkpoint = Checkpoint(
            epoch=previous_epoch,
            root=get_block_root(state, previous_epoch)
        )
        state.justification_bits[1] = True
    
    if current_epoch_target_balance * 3 >= total_active_balance * 2:
        state.current_justified_checkpoint = Checkpoint(
            epoch=current_epoch,
            root=get_block_root(state, current_epoch)
        )
        state.justification_bits[0] = True
    
    # Finalization 规则
    # 检查连续 justified 的检查点
    bits = state.justification_bits
    
    # 2-1 finalization: epoch N-2 → N-1 都是 justified
    if all(bits[1:3]) and state.previous_justified_checkpoint.epoch + 1 == previous_epoch:
        state.finalized_checkpoint = state.previous_justified_checkpoint
    
    # 1-0 finalization: epoch N-1 → N 都是 justified  
    if all(bits[0:2]) and state.current_justified_checkpoint.epoch == current_epoch:
        state.finalized_checkpoint = state.previous_justified_checkpoint
```

#### 4.2.3 Slashing 条件的数学证明

**定理**：如果两个冲突的检查点都被 finalized，则至少 1/3 的质押必须被 slash。

│                      长程攻击防护机制                                    │
├─────────────────────────────────────────────────────────────────────────┤

│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                                                                  │  │

│   │                                                                  │  │

│   │                                                                  │  │
│   │   如果攻击者获取了 B 时刻的旧验证者私钥（已退出）：              │  │
│   │   • 可以签名替代链上的区块                                       │  │

│   │                                                                  │  │

│                                                                         │

│   │   ──────────────────                                             │  │

│   │                                                                  │  │

#### 4.4.3 常见攻击场景分析

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      攻击场景与防护                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   1. 短程重组攻击                                                       │
│   ───────────────                                                       │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │  攻击者拥有 <1/3 质押，尝试重组最近几个区块                      │  │
│   │                                                                  │  │
│   │  防护：                                                          │  │
│   │  • LMD-GHOST 实时计算权重                                        │  │
│   │  • 诚实多数快速收敛到规范链                                      │  │
│   │  • 攻击成功率随区块深度指数下降                                  │  │
│   │                                                                  │  │
│   │  安全深度：~4-6 个区块后重组概率极低                            │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│   2. 平衡攻击（Balancing Attack）                                       │
│   ─────────────────────────────────                                    │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │  攻击者尝试让网络在两个分支间摇摆                                │  │
│   │                                                                  │  │
│   │  攻击方式：                                                      │  │
│   │  • 战略性延迟发布区块或投票                                      │  │
│   │  • 让两个分支权重交替领先                                        │  │
│   │                                                                  │  │
│   │  防护（proposer boost）：                                        │  │
│   │  • 区块提议后立即获得临时权重提升                                │  │
│   │  • 提升值 = 40% of committee weight                             │  │
│   │  • 防止攻击者通过延迟策略操纵                                    │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│   3. 验证者贿赂攻击                                                     │
│   ─────────────────                                                    │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │  攻击者贿赂验证者进行恶意投票                                    │  │
│   │                                                                  │  │
│   │  经济成本：                                                      │  │
│   │  • 需要贿赂 >1/3 质押的验证者                                   │  │
│   │  • 这些验证者面临 Slashing 风险                                 │  │
│   │  • 贿赂金额必须 > 潜在惩罚                                      │  │
│   │                                                                  │  │
│   │  当前成本（34M ETH 质押）：                                      │  │
│   │  • 贿赂 1/3 = 11.3M ETH ≈ $220 亿                               │  │
│   │  • 加上 Slashing 损失 = 更多                                    │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 6.3 设计权衡与反思

| 设计选择 | 优势 | 代价 |
|---------|------|------|
| **大规模验证者** | 高度去中心化 | 最终性延迟较长 |
| **32 ETH 最低门槛** | 个人可参与 | 验证者数量巨大 |
| **2048 ETH 上限** | 减少验证者数量 | Pectra 后引入 |
| **12 秒区块** | 用户体验好 | 网络同步要求 |
| **2 epoch 最终性** | 安全性高 | 确认时间长 |
| **BLS 签名** | 聚合高效 | 计算密集 |

## 附录 C：重要公式汇总

**1. 基础奖励**

$$\text{base\_reward} = \frac{\text{effective\_balance} \times \text{BASE\_REWARD\_FACTOR}}{\text{BASE\_REWARDS\_PER\_EPOCH} \times \sqrt{\text{total\_active\_balance}}}$$

**2. 年化收益率近似**

$$\text{APR} \approx 2.6\% \times \sqrt{\frac{1,000,000 \text{ ETH}}{\text{total\_staked}}}$$

**3. Slashing 相关性惩罚**

$$\text{penalty} = \frac{\text{effective\_balance} \times \text{slashed\_balance} \times 3}{\text{total\_active\_balance}}$$

**4. 攻击成本下限**

$$\text{attack\_cost} \geq \frac{1}{3} \times \text{total\_staked} \times \text{ETH\_price}$$
